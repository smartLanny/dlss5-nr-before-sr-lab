# 后置私有 SR：输出合同精确分类

2026-09-22。开发侧只读分析，继承实验 HEAD `f6bae478`，没有修改旧实验、
生产 Core、颜色算法、shader、运行时门禁或菜单。既有四项 dirty 内容已另存
私有备份并逐项核验未变。本次仅新增分类工具、CPU 合同测试和本文。

## 结论

同一批五份实际 NR → 私有 Feature1 的保存结果应分类为 **FP16 中合法的有限
越界值**。它们违反旧宿主的严格 `[0,1]` 数值合同，但不是 NaN/Inf、FP16
溢出，或仅凭越界就能断定的颜色域错误。

这项更精确的归类没有把结果升级为画质验收通过。FP16 可以存储这些值，
不表示后续编码、显示或 UNORM 目标能够不失真地接收它们。五例还是人工
静态导引、单次 Reset 的离线实验，不足以接入生产 Core。

## 旧拒绝到底检查什么

- `tests/post_residual_ngx_host.cpp` 的 `Run` 对最终 FP16 RGB 累加
  `outside += ov < 0 || ov > 1`，另计私有 SR 载体的越界。最终
  `outside || carrier_outside ? 4 : 0` 是宿主数值拒绝，不是驱动错误。
- 同文件 `Value` 会先拒绝 FP16 指数全 1 的 NaN/Inf；这种失败与 exit 4
  的有限范围拒绝不同。旧总体 `numerical-refusal` 名称没有呈现这个区别。
- `shaders/nr_post_residual.hlsl` 的 `ComposeCS` 最终写入条件是 RGB
  有限且绝对值不超过 65504；没有把最终 RGB saturate 到 `[0,1]`。
  已有 `saturate(carrier)` 是载体解码边界；五份实际 SR 载体全部在 `[0,1]`，
  因此该操作没有裁去本批载体通道。本文不修改该编码合同。
- 所以旧严格拒绝在原先“最终必须为有界 SDR”的实验合同下是正确执行；
  把该拒绝进一步表述成“FP16 存储非法”或“颜色域必错”则不成立。

## 四个互相独立的轴

| 轴 | 本工具检查 | 不能由此推导 |
|---|---|---|
| 证据/颜色域 | 重查原 NRF、生产者与模型回执，运行既有显式 IEC sRGB 转码；要求 B/Z 包逐字节重生成一致 | `[0,1]` 范围本身不能证明是线性或编码域；最终轻微负值也不能证明转码错误 |
| 数值健康 | RGB 的 NaN、+Inf、−Inf 分开统计，alpha 另验；分区总数必须与像素数一致 | 格式能表示 NaN 不代表其可作为有效颜色 |
| FP16 与有界 SDR | 有限 FP16 与 `[0,1]` 越界分别报告；保留实际 min/max、正负计数、影响像素数 | 有限越界不自动获得生产采用资格 |
| 最终目标 | 列出假定写 UNORM 时必须裁剪的有限通道及范围损失 | 没有执行 UNORM 存储、量化、额外 transfer function 或实际显示验收 |

微软 [DXGI 格式说明](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format)
将 FLOAT 与 UNORM 分为不同数值类型；[数据转换规则](https://learn.microsoft.com/en-us/windows/win32/direct3d10/d3d10-graphics-programming-guide-resources-data-conversion)
规定 FLOAT → UNORM 在量化前把范围外值限制到 0 或 1。本表只报告这个必然的
范围损失，不模拟 GPU 量化舍入，也不把 UNORM 转换用于掩盖 NaN/Inf。

## 相同五份样本的实际分类

仍使用原 `post-real-sr-unified7-r3`，并与其 `storage-audit-final.json` 的哈希、
每例计数及最值核对。原始宿主编译基底仍为 unified7 `a627f28b`；本工具没有
再次调用 NR/SR，没有更换模型做 A/B，也没有重渲染或改写任何保存像素。

每例 640×360、230,400 像素、691,200 RGB 通道；工作网格 160×90。

| 层数 | 有限越界通道 | 影响像素占比 | RGB 通道占比 | 实际最小值 | 实际最大值 |
|---|---:|---:|---:|---:|---:|
| 1 | 805 | 0.34939% | 0.11646% | −0.0032844543 | 1.0087890625 |
| 2 | 1,684 | 0.73090% | 0.24363% | −0.0035896301 | 1.0117187500 |
| 3 | 2,073 | 0.89974% | 0.29991% | −0.0032272339 | 1.0117187500 |
| 4 | 2,561 | 1.11155% | 0.37052% | −0.0035705566 | 1.0107421875 |
| 5 | 2,289 | 0.99349% | 0.33116% | −0.0032882690 | 1.0107421875 |

本批每个受影响像素恰好一个 RGB 通道越界，故通道数等于影响像素数；这不是
分类工具的假设。五例 NaN/+Inf/−Inf 都是 0，alpha 与 B 的保存字节相同。
所有 B/Z 的显式转码包重生成一致，实际 SR 载体也都有限且在 `[0,1]`。

越界幅度使用编码值单位，描述分箱为 `(0,1/1024]`、`(1/1024,1/255]`、
`(1/255,1/64]`、`>1/64`。五例最后一箱均为零，但 **1/64 不是批准阈值**，
不据此放宽任何门禁。报告保存分箱、p50/p95、正负最大幅度、影响区域和示例。
“轻微”应配这些数值阅读，不能替代终端颜色语义或运动稳定性验收。

若目标是 UNORM，上表每个越界通道都会损失其越界部分。这是反事实裁剪成本，
不是已经执行的修复。没有做全帧回退、逐像素替换、夹持或比例调整。
原审查中空间对照也存在越界的事实保留，不能把全部差异归咎于 SR 模型。

## 负控与复现

每份实际样本在内存中派生相同六类控制，旧证据不改：

1. 把原始 LinearSdr B/Z 冒充编码域：所有值仍在 `[0,1]`，但来源哈希证明
   缺少显式转码，归为 `proven-linear-bytes-in-encoded-contract`。
2. 已转码字节使用错误域声明：独立拒绝声明不匹配。
3. 第一个 RGB 写入 NaN、+Inf、−Inf：三者分别检出，不混入有限越界计数。
4. 第一个 RGB 写入 −1/1024、1+1/1024、1.125：都为有限 FP16，分别进入
   小/大幅度箱；严格 SDR 仍不通过，不能伪装成非有限错误。
5. 输入改一个字节：不能沿用旧转码证明，归为未验证载荷域。
6. 输出证据改一个字节：原保存回执的哈希检查准确拒绝。

六种机制 × 五个旧样本 = 30 个派生检查；仍只有五个实际模型样本。
另有七项快速 CPU 合同测试覆盖 signed zero、最小 subnormal、最大有限 half、
alpha NaN、shape 和来源证明。它们不计作 GPU 或图像质量场景。

```text
python experiments/nr-edit/tests/test_post_output_contract.py
python experiments/nr-edit/tools/classify_post_output.py --validation <post-real-sr-unified7-r3/validation.json> --storage-audit <post-real-sr-unified7-r3/storage-audit-final.json> --output <fresh-private-directory>
```

分类回执标识：`post-output-contract-r1`。结果 `classification-completed` 表示
分类过程完整，并非 SR 图像被批准。所有旧 exit 4 保留在新报告中。

## 接入 Core 前仍缺什么

- 真实源帧下 B/Z 的同帧、同活动区域、最终层选择与颜色域证明；现有数据来自
  受控 NR 捕获再离线转码，不是生产后置调用链的即时资源证明。
- 实际运动和深度导引：源帧/曝光、低高分网格、MV 数值单位与方向、有效 scale、
  jitter 相位、depth 投影/反转、遮挡及 disocclusion 都须有真实来源。
  人工 depth=0.5、MV=0、jitter=0、每例 Reset 不能替代这些证据。
- 连续帧历史、零/微小编辑的出现与消失、移动/遮挡及历史退休；本次没有验证
  该载体的运动重建质量，也未验证把原生 SR 导引挪给最终残差网格是否成立。
- 最终消费者的明确合同：FP16 允许的有限扩展范围、后续编码/显示流程或最终
  UNORM 量化必须单独验收；“存得下”不能决定“应该显示”。
- 真实 Core 调用顺序、原生调用一次、不可变描述符、实际 fence/录制 lease、
  部分 opaque 失败隔离、热切换，以及严格整数 25% 尺寸边界。

因此当前结论是“纠正拒绝原因的归类，并保留真实数值”，不是允许 Core 上线。
