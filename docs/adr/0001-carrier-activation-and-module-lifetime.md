# Carrier 以实际修复为目标，采用两阶段激活和 Hook 模块进程寿命

维护者要求继续实现 carrier 修复，接受已 Hook 的相关 DLL 留到游戏退出；本计划以 #185 两阶段原型作为当前生产化路径。正常 D3D11 候选期只观察真实 Create/Release，确认同设备交换链及成功创建记录后才允许完整桥接，避免在加载通知中执行繁重初始化；缺失早期创建记录时保留原生路线，不伪造历史。

模块保留只覆盖 Hook 代码依赖，不扩大为 device、NGX 实例或共享纹理永久驻留。维护者选择了这一寿命策略，而非要求本阶段支持运行中完整卸载和重载 Hook 模块，因为后者会显著扩大并发退役范围。

## Consequences

- 必须把原型接到真实生产 Hook/回调与资源退役；只交状态机或普通 DLL 测试不满足修复目标。
- 晚加载而漏掉 Create 的句柄可暂时不支持 NR，必须明确说明。这个保护行为不能替代对原始崩溃和游戏可用性的实际修复验收。
- 不将 #185 的设计选择认定为 BG3 等崩溃的已证实根因；若实际证据指向更小或不同缺陷，按证据修复。
- Manager 的明确 API 部署/排除与运行时保护继续共同使用，不因运行时改造删除部署保护。

本决策已确认；本次文档任务仅做规划，未实施该生产改造。
