## 3. 三条并行工作线

### A. 其他 API 游戏兼容与实际 carrier 修复

关联：#153/#106/#164/#14/#165；既有 #175/#185；随后 #99/#123/#121/#148/#139/#140。

1. **接续和整合现有修复。** 检查真实 ancestry、当前文件占用和 source transformation
   的输入锁；沿现有 PR 交付，不另建竞争 Core/Feeder/诊断系统。独立保留 0.5 与 Manager。
2. **#185 从原型进入真实实现。** 加载通知只写有界事件与 generation；扫描、日志、
   Hook 安装/移除、模块引用处理和资源释放放在 loader lock 外。复用已有 Hook 能力，
   验证真实 Create out-handle、成功结果和 Create/Release 恰好一次的语义。
3. **实际 DX11 才完整桥接。** 候选 D3D11 device 只轻量观察，同一设备的交换链及
   已观察成功的句柄才允许开启私有桥；辅助设备、其他 API、未确认/已释放句柄不得
   误激活。Manager 的明确 API 选择与部署保护继续适用，不能仅凭 EXE 导入猜 API。
4. **补真正的寿命合同。** 仅为实际 Hook 依赖保留模块；处理同址重载 generation、
   事件溢出安全 rescan、Create/Release 与 destroy 并发、多 swapchain、device 变化、
   等待中的 GPU 工作和最终退役。不能让 DLL pin 变成永久保留纹理/NGX 实例的借口。
5. **失败不伪装修复。** 漏 Create 则明确 incomplete/native fallback；不伪造 flags、
   Reset 或 owner，不删除 unknown-handle 保护，不在污染的命令列表上盲目重跑原生
   调用。若实际错误涉及尚未证实的完成状态，继续使用既有隔离边界。
6. **用 BL3 验证真实输入。** 下载未完成时并行推进 B/C 和 carrier，不打断下载。
   就绪后重新锁定 EXE/build/API/runtime。先观测真实颜色、深度、运动、jitter/reset、
   曝光、有效区与帧身份，再做 SR-only/DLAA、回退、接自有 NR，最后降低真实 R。
   DLAA/R=O 只算中间阶段，不能对外称已经实现真正超分。
7. **允许换稳定桥。** 若本项目桥不能稳定完成该路线，用已有稳定 carrier/输入适配
   或 Luma 接点先打通；明确桥、provider、NR owner、SR backend 的各自身份。不能
   悄悄改用另一套 NR 并把成功算到本项目 Core。
8. **实际崩溃验收。** #153 以可复现游戏症状、候选稳定性和具体证据判断；如果尚不能
   复现原错误，只写候选防护/部分修复，Issue 不因新架构或普通 DLL 测试自动关闭。

第一条真实非 DX12 路线通过后，沿可靠输入与成熟桥继续扩其他 API。Vulkan/layer
安装与资源传输由 #165 两侧配合；界面可选某 API 不等于已支持该 API 的 NR。

### B. 默认单次 NR 强化的画质与性能

关联：#71/#168/#169/#11/#84/#85/#86/#113，计量 #9/#10/#90/#91；已有 #170→#172。

1. 先审查并集成 #172 已有候选的真实接线与开关，不重复实现输入核、恢复核或 EditField。
   保留 Exact Area、Bilinear、旧前/后置参考与默认关闭/回退路线。
2. 默认推荐保持单次 NR、效果倍率 1.0、NR 工作比例主 UI 50–100%；接续 #183 的新装
   100%及旧配置保留。NR 色调跟随与整体倍率仍分别解释和执行。
3. 在一次推理的残差/编辑场中继续研究更接近叠层的观感，逐变量比较亮度、色度、结构、
   低频光照和边缘保护；不能通过全面削弱 NR、去色或降曝光制造指标改善。
4. 多次 NR 仅实验：先两层、同 N、单视图和固定工作尺寸，独立 history/reset；核实
   第二层图像相位与其 MV/depth/jitter/exposure 的关系。不能从 Reset=1/zero-jitter
   的有限样本直接开放连续时域级联，也不急于同时扩 3 层、动态尺寸与多视图。
5. 相位未明时保持已知范围的隔离实验，日志明确 unverified。比较第二层的实际收益
   与成本，反向指导单次强化；实验成功不预先等同于默认应该叠层。
6. 人脸独立保护和新分割模型延期。允许对 #162 现有开关问题及直接 mask 原理做有界
   调查；没有可靠可读来源就保留缺口。#184 人工 mask 不进入普通产品当作人脸识别。
   未来独立人脸强度不受全局倍率覆盖，具体默认值和量程在功能恢复开发时再落实。

**5% 的可执行口径：** 固定同场景、同 R/N/O、模型、风格/强度及预热条件，用同一
设备/驱动比较现有参考与默认单次 NR 候选；报告源帧 GPU 中位耗时、P95/P99和显存。
默认候选的 GPU 中位和 P95 增长均以 5% 为上限，不用插帧后 FPS 抵消成本或掩盖长尾。
性能采样与图像/详细日志采集分开。若计时证据不足则写“未确认达标”。多次 NR 属于
显式实验，不受默认档的启用承诺，但额外成本必须如实展示。

### C. Manager 优先交付 40/50 系 FG/MFG

关联：#179/#181/#16，现用产品已有 SR/FG writer、组件准备、事务和恢复；
注入式 FG 另见 #167/#173，不能混称。

1. 只在本仓现用 xiaofeng UI 继续。先核对 #181 最新 HEAD、已安装版本、清单和未完项，
   不重做已完成的 SR/FG 设置服务、40 系组件准备、50 系原生策略或后台扫描优化。
2. 40 系路线检查所需兼容组件、实际游戏 FG 能力与加载入口，完整准备后再提供设置；
   50 系走已支持的原生固定/Dynamic 方案。未知能力不按 GPU 型号强制猜倍数。
3. 设置、组件与恢复共用现用事务，保持 EXE 绑定、原件和逐键继承恢复；不并列第二套
   writer/journal。文件/驱动写入失败、EXE变更、外部修改和启动失败都要留下可恢复结果。
4. 用户接受稳定 Manager 设置管理作为 MFG 里程碑；不要求先给原本没有 FG 的游戏
   注入新 FG。实际 40/50 游戏验证缺哪一类就明确保留，不借一台机器或内存驱动替代。
5. #167/#173 的新注入式 FG 只推进能带来实质进展的有界切片。新的 A/B 样本或游戏
   探索可以作为实验选项，用于采集真实输入、执行结果和失败日志；不得仅因 SDK
   presented 计数增加就显示“真实插帧已验证”。
6. 新实验不强制覆盖现用 Core 载荷。进入包前独立核对 Core/Manager/carrier 的来源与
   兼容关系，保持语言包、OTA和便携版身份一致。

## 4. 测量权限与游戏操作

- 已允许指定工具使用管理员权限和长期采集能力。优先利用正常管理员启动方式或
  所需的最小采集权限；不绕过 UAC/凭据安全机制，不把授权解释成任意系统改动。
  无交互无法完成系统确认时，记录实际执行条件，不反复询问已经确认的开发方向。
- 当前 PresentMon 的 access denied 是执行条件，不是 FG 原理失败。获得权限后先
  核实 PID/swapchain/time、事件类型和丢失情况；unknown 仍保留。显示事件、生成
  像素与物理屏幕节奏/端到端延迟分别记录，不能用一份 CSV 证明所有层次。
- 长期采集指可跨目标游戏测试持续使用的采集能力；限定目标进程、使用有界文件和
  滚动保留，默认本地保存。不得无界增加原始日志、录屏或自动上传。
- 目标游戏允许先备份再临时部署/启动/采集/恢复。尚未给固定时段时，不抢占维护者
  正在玩的游戏，不改动正在下载的 BL3；优先空闲/隔离条件，最后集中交维护者测试。
- 不为本计划启动长期轮询旧 F8 的任务。已有 RR 修复与旧反馈继续沿用，只有新的
  具体回归才追加针对性检查。

   版本身份，也不把未验算法设为普通玩家默认。**main 合并必须晚于维护者验收。**
6. 最终给维护者一份集中测试清单，按目标游戏/API/版本列少量关键步骤：原生对照、

   视觉异常才补 F7；不让维护者重复跑已经确认的旧 RR 测试。

可分发组件按实际来源和允许范围处理。本计划不要求改系统驱动、HAGS或无关账户。
