# D21 Perf4：实测外层范围扫描与来源满表重复工作的修复

## 目的与基线

关联 #277、#272、#273。维护者授权在 Perf3 实测基本未改善后继续性能修复。
已重新读取在线 main `dae86e9898399c20e52ada54a5ec4350da4d4fa1`、开放 Issues/PR 和性能分支。
本轮从已测试 Perf3 源码链 `c144d7cb8553f19972ab4b20a88b13dea1b69b94` 建立隔离分支，研究目标仍为 `next/0.5`。
不更改主线、旧测试包、独立画质分支或游戏目录。

上一轮 ETL 与精确二进制/链接映射显示：描述符热点落在 heap×range 外层候选检查；Lineage 热点落在 64 批次无空位后每次失效 256 标签的分支。
Perf3 的小范围槽访问和普通批次缓存微基准没有覆盖这两个路径。Perf4 的反馈循环先让原 Perf3 在这两个实际机制上失败，再验证新实现。
不能把任何微基准数值解释为游戏 FPS 收益。

## 运行时修改：仅两个头文件

### `src/nr_descriptor_provenance.h`

复用已存在的、按起始地址排序并带前缀最大结束地址的 CPU heap 范围索引。
以每个未知范围为查询条件，二分定位可能相交的范围上界，沿前缀最大值反向筛选所有真正可能相交的 live heap。
512 字节固定 scratch bitset（默认 4096 heap 容量）去重；最后按原 heap 顺序执行原来的逐槽失效逻辑。

这不会改变调用者的 range 数组，不会只挑一个重叠 heap，也不会改变描述符类型、精确边界、pending、overlap、revision、epoch、COM 寿命或读取/发布顺序。
不读取 native 描述符内容、不新增堆分配，不改变注册表对象大小或锁顺序。

大范围从首项就覆盖整个已知地址跨度时直接保留旧方式；其他密集/对抗性重叠扫描超过固定候选工作预算时，丢弃部分候选集，完整回退原过滤，而不是漏掉剩余范围。
原有精确槽索引优化和 sparse/broad 单 heap 逻辑保持不变。重叠或稀疏极端配置的收益不保证，须保留回退。

### `src/nr_source_frame.hpp`

满批次表仍返回失败、仍让已有来源未知，不扩大表、不淘汰或复用尚未退休的批次。
两个局部优化：

1. 对四个完整 `(list, lifetime, reset, device)` 失败键做有界负缓存。没有空位时，旧失败键不再做重复全表查询；Reset 或 ForgetList 释放任意位置时清除此缓存。有效批次命中仍核对完整身份。任意数量的新键仍安全回退查找。
2. 记录“全部已发布标签是否已处于 Unknown 的不动点”。第一次容量失败仍逐项执行原 Unknown 转换，保留 tainted、fg_consumed、encoding；在没有新发布的情况下，重复 Unknown 没有新语义，省掉重复写入。Submit（包括失败提交）、Presented、RetireSource 会重新置脏，使下一次失败必须再次失效。

DescribeSurface 只改 Unknown 本来会保留的 encoding；Forget 只清为同样的不动点。它们不需要重新失效标记。
事件暂存不是标签发布，事件的 Set/Copy/Clear/Invalidate 仍按提交顺序处理；缓存不跳过事件或恢复检查。
原外部 source_lock 的独占同步没有改变；对象复制只复制值/相对索引，不产生悬空指针。

**这减少了满表失败路径的成本，但不代表容量不足已变成成功、不代表新增来源可以越过安全门禁。**

## 验证

`scripts/validate-perf4-hotpaths.py` 从冻结 Perf3 Git 对象读取旧生产头文件；新头文件直接来自工作源码。
只在临时计数测试副本中插入工作量计数，普通微基准和交付 DLL 没有这些计数器。

- 1024 heap / 128 range 场景：旧候选检查 245,888 次，新 512 次。二分过程另有常数/对数比较，不包含在这一计数中；完整微基准同时测量整个调用。
- 64 个批次满表后 16,000 次失败调用：旧标签重写 4,096,000 次、新 256 次；旧批次表检查 2,048,000 次、新 320 次。失败返回与全部标签的安全含义不变。
- 3000 步饱和/重新发布/提交失败/退休/Reset 差分，周期性检查全部 256 标签；源对象复制、批次释放后重新登记继续与旧实现一致。
- 多 heap、重复/交错 range、不同类型、嵌套 unknown scope、heap 退休及既有未对齐/高地址/重叠精确 receipt 差分通过。
- Perf3 原负控/正控、120,000 操作描述符差分、8,000 多线程生命周期、描述符 CPU 2,225 检查、来源策略 399 检查通过。
- 普通无计数微基准同时测试疏散范围与密集地址跨度，不只测试最有利输入。保留原始耗时回执，不能外推到 GPU 或真实弱 CPU 帧率。

本轮未修改 NR 数量、分辨率/subrect、SR/RR/FG 路由、shader、HDR/色彩、jitter、MV、depth、exposure 或任何画质参数；未关闭 hook。
首次初始化/关闭切换长帧、槽哈希链查询、静态资源描述缓存、更多用途筛选保留为独立后续方向，不混入本次验收。

## 构建与交付

入口 `scripts/build-perf4-candidate.ps1`，继承 Perf3 的全部 Windows/SRW/源身份/完整编译/WARP 和负控，追加 Perf4 的两个失败路径测试。
旧 Perf3/Lock2 入口转发至当前构建，不把新二进制错标为旧版本。
版本为 `beta0.5-dline21-perf4`；数字 PE 版本仍继承，区分构建必须用版本字符串、实际源码提交和 SHA256。

新增可选 `CodecCacheRoot` 只向已有严格 codec 缓存验证器传递路径：它验证重新编译的 compiler PE（仅允许时间戳差异）、源/选项和逐 DXBC 哈希。原始 shader 回执保留；所有 WARP、静态分析和 Core 编译仍执行。它是构建加速，不是游戏路径改动。

`package-perf4-ota.py --candidate <validated-output> --output <new-ota-dir>` 要求 canonical、SRW、Perf3、Perf4、完整描述符 WARP、来源 WARP 和快照读回负控回执通过，才输出一个中文 Core 与自有 nrchain。
包含说明/许可证/逐文件清单；不包含 INI、模型、NVIDIA 游戏运行库或调试映射。校验 x64 PE、嵌入版本/源码、companion 导出、ZIP CRC 和逐文件哈希。不自动部署、不发布 Release。

机器没有调试层时，可显式延用 `AllowMissingDebugLayer`，但回执必须保留 `snapshot_debug_layer_verified=false`。真实 WARP 字节读回和错误像素负控仍必须执行。调试层、托管 CI、游戏/NVIDIA 推理是独立状态。

## 实测验收与风险

新包运行时必须只加载一个 Core，并使用匹配的 nrchain；保留旧包备份、原 INI、模型和桥接器。
与 Perf3 比较同镜头同参数的首次 OFF、单层 NR→SR ON、再次 OFF，确认成功计数增长，再核对帧时/ETL 中的两条旧热点。
满表失败仍可能限制来源可用性；缓存只消除重复成本。稀疏/密集范围、Reset/资源/列表重建、RR/FG 和多设备边界仍需实际游戏回归。
若持续旁路、无效果、闪烁或崩溃，回滚并上传 F8、Core 日志、版本和哈希反馈 BUG；旁路不能算作提速。
本文件中的 CPU 测试不证明任何游戏收益，最终可安装产物与实测状态见交付回执和 PR 更新。
