Related to #277, #272 and #273. Research target remains `next/0.5`; no main/stable
merge, release, game deployment or unrelated colour/uniform integration.
Base: owner-tested Perf6 `8baa048cade9bb10b0108c77ad4e014717b49377`.
Online main and open PRs/branches were checked before development; main remained
`dae86e9898399c20e52ada54a5ec4350da4d4fa1` with no competing tracking successor.

The owner explicitly requested a coherent whole-path repair, not another isolated
micro-optimization followed by a new capture. This batch addresses related
identity lookup, immutable device-cookie reuse, legacy resource-state indexing,
and within-call identity reuse together. It does not claim maximum possible
performance, and synthetic work reductions are not game-FPS improvements.

## Production changes and safety boundaries

### Exact legacy resource-state table

`nr_source_state_table.inl` replaces only the source observer's 256-entry linear
legacy-state table. It retains 256 entries, original first-free admission order,
full recording+resource identity, no eviction, and unknown-on-capacity behavior.
A 512-bucket full-key index and a checked relative MRU remove repeated scans.
Single deletion repairs the probe cluster; recording/lifetime/resource retirement
rebuilds the index only when entries actually change. There is no heap allocation,
COM ownership or actual D3D12 state transition in this metadata table.

The key includes list/lifetime/reset/device plus resource address/lifetime/device/
subresource. Aliasing and enhanced barriers still invalidate whole-recording
legacy evidence; split or partial-subresource barriers still invalidate the
specific whole-resource evidence rather than pretending it describes all
subresources. Reset and destruction use the same lifetime/address predicates as
the original implementation. `Get`, including its checked MRU, requires the
existing EXCLUSIVE `source_lock`; all production callers were checked.

### Batch-local resource identity reuse

Inside a single `OnBarrier` call, a fixed 16-entry cache reuses successful
resource/device identity queries for repeated native resource pointers. It is
stack-local, lives only for the borrowed native call, and is never reused across
calls, Reset or destruction. Failed identity queries are not cached. Event order,
lineage taint and pending-submission publication remain unchanged.

Pure UAV ordering does not produce legacy-state evidence, but `RecordingOf` can
publish a canonical device receipt. The final implementation deliberately keeps
that identity lookup and lock even for pure UAV batches; it only avoids unused
state-table/scratch work afterward. Native barriers are never omitted. An early
pre-lock reject was evaluated and rejected because it would remove this identity
side effect. This is not a policy that ignores UAV dependencies.

### Related command-list identity lookups

`nr_source_observer.inl` uses checked relative-slot hints for observed lists;
readiness, lifecycle, device and reset are read freshly, with no negative or
readiness cache. `nr_post_boundary_native.inl` expands its single-entry TLS native
lookup to 16 bounded entries, still under the registry shared lock and guarded
by the existing epoch. Negative native hints always consult the CURRENT alias
scope; no validated proxy mapping survives outside its original call.

`nr_source_frame_runtime.inl` avoids the redundant observed-list scan when the
owned device is already known, indexes the canonical device-cookie lookup with
full address/token checks, and reuses an immutable cookie only for that exact
Core lifetime. Cold seeding remains the only COM/device lookup boundary; normal
Evaluate no longer repeats it for already-known lifetimes. The hint hash handles
correlated list-address/token sequences, explicitly tested after an initial
collision-prone hash failed the work budget.

No native queue/list/resource lifetime guards, state restoration, pipeline
bindings, shader, model, layer count, resolution/subrect, jitter, depth, motion,
exposure, HDR or NR/SR/RR/FG routing is intentionally changed. Existing registry
and source locks remain; this is not a lock-free rewrite or drop-update shortcut.

## Executable feedback loop

`validate-perf7-tracking.py` extracts the actual old/new runtime bodies rather
than reproducing an alternative algorithm. Test-only counters are injected into
temporary source copies; shipped code has no added per-iteration timers/logging.

- The frozen Perf6 budget fails: 65,152 state comparisons and 256 ResourceOf
  queries for a 256-transition batch updating four hot entries of a full table.
  The new production body performs 1,024 probes and four resource queries.
- 300 capacity-fill operations followed by 3,500 mixed barrier batches compare
  the old/new results. Include UAV, aliasing, enhanced, split/subresource, null,
  disabled, reset/lifetime changes, resource destruction and full-table refusal.
- Eight interleaved lists over 16,000 calls: native snapshot full scans
  32,712,000 -> 0, observed-list scans 4,040,000 -> 0, device comparisons
  72,000 -> 16,064. Complete identity validation still executes on every hit.
- 1,000 repeated Evaluate seed calls: COM device queries 1,000 -> 0 once the
  exact canonical lifetime is known. Alias/native selection and fallback are
  compared before/after readiness, Reset and same-address republishing.
- Real Windows SRW test: 40,000 concurrent snapshots across 4,998 writer
  generation changes retain one coherent identity. Non-Windows test builds use
  explicitly labelled synchronization doubles, not native-SRW claims.
- The existing compatibility-route suite executes with an explicit compiler;
  it must not silently skip its native/alias and 36 production-suffix checks.
- Existing generation/workflow tests pass. Full inherited Windows/descriptor/
  state-restoration/WARP gates remain required by the candidate builder.

Uninstrumented CPU timing includes identity stubs and the actual observer body.
Repeated/dense transition tests improve, but the ideal single first-slot update
microcase has roughly 10 ns additional overhead per call (about 0.02 ms over
2,000 calls). That isolated case is disclosed, not described as faster. No CPU
microbenchmark is a hardware-driver, game-FPS or no-regression guarantee.
