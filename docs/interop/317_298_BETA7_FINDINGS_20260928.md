原始 log tail 多次交替 generation=5 / 130，并在 generation=130 后记录 `[RR-depth] rejected at slot-not-retired; native RR retained.`。这比始终存在的 FG-owned Present 状态更直接。快照是独立原子读数，计数关系与日志相互支持，但不冒称已逐帧锁定玩家看到的每一次闪烁。

代码链：`ProcessRrPost` → `PrepareAfterSr` → `FindOrCreateSlot` → `EnsureRrDepthSlot`。槽选择允许同资源在已证明同队列顺序下继续使用；首层调用却省略 `immutable` 参数，进入默认 mutable 分支，每次先要求 `CanMutateSlotLocked`，以便重写槽上的深度 SRV/UAV。存在录制引用或未完成 fence 时，本可用不可变描述符追加的工作被拒绝。辅助层已经调用 `EnsureRrDepthSlot(..., true)` 并通过 `AcquireBindingPacket` 保留独立描述符和资源。

不能只把首层的 bool 改为 true：现有 `nr_regions::Seal` 在 region 未启用时直接返回，且原先不生成首层 Depth 描述符；必须同时接好首层不可变 Depth plan、录制租约及失败旁路。真实深度平面缺失/尺寸变化仍必须经过原有槽完成与绑定失效检查，不能删除 fence/queue/recording/隔离保护，也不增加 CPU 等待。

## Finding 2 — scope.nrSuccess 归零不是同一个统计作用域倒退

同一 F8 的 scope.epoch 从 491 变为 509，期间日志中 generation=5 / 130 交替。`BeginPipelineStatsScopeLocked` 遇到来源代次或模式变化会递增 epoch 并清零局部计数。因此不能直接相减 scope.nrSuccess=1→0，也不能据此断言 F6 开关被关闭或 NR 模型历史被清空。全局 nrSuccess=45976→45989 与后置录制 +13 一致。

uiActivity 的 reset=16 明确为 pipeline-epoch 变化，窗口持续重新建立；它是观察记录，不是 uiActivity 主动暂停渲染的证据。诊断日志中的字面 `Feature1 generation` 是共享函数标签，也不能单靠这个字面认定该次调用必为 Feature1。

## Finding 3 — #298 第二层实际有录制采用，fullNR=0 属于非当前统计

来源：`bug-reports/bug-inbox/issue-298/20260928-qq-2651934308-htgame-0.5.2-beta.7-占用/260928-htgame-0.5.2-beta.7-204119146-21336-1.txt`，SHA256 `93f0979886e24c6cd33d8016035532c624c5de1fe213c77193a13f079761aa70`。

请求 activeLayers=2；但 `fullNR.scopeMatches=0`、`fullNR.enabled=0`，其中 requestedPasses=3、lastAdoptedPasses=0、实例=0 都不能代表当前双层路线。实际双层统计：

- dual.status=4，snapshot.state=active；主层/次层均为 2304×1296，实例为 1 / 2。
- dual.evaluateSuccess=2611→2633，completedStableSamples=2608→2630，分别 +22；createCalls=1→1。
- 两个 snapshot 的 finalAdopted 分别为 7、14，均为非零；windowStart 不同，不把 14−7 当作整个 F8 区间的采用总量。
- livePrimary=1、liveAux=1，retired/pending/quarantine 均为 0；auxTrackedBytes=77,856,768，start/end 相同；没有该窗口的退休堆积或辅助创建增长证据。

结论：不能以 lastAdoptedPasses=0 推断“第二层占显存却没有采用”。这是两个独立模型实际执行的短窗口；仍不等于最终显示/全程无故障证明。
