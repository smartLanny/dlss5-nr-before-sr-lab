## 新的 Perf8 / Perf9 对照

两份原始 ETL、CSV、manifest 和 F8 均重新读取和 SHA256 核验，目标进程
分别为 52304/34296。都为单层 NR→SR、2228×1253 NR、2/2/2、skin=-1、
UI correction=1。各自 NR 成功次数在停止后保持 739/892，没有持续旁路提速。
所选阶段无编译器 CPU 采样；但 Perf8 同期安全扫描约使用 1.9–2.0 核，
Perf9 有多个 PowerShell 进程，不能声称后台完全一致或无测量噪声。

| 阶段 | Perf8 FPS | Perf9 FPS | Perf8/Perf9 插件 self CPU ms/s |
|---|---:|---:|---|
| 首次 OFF | 81.09 | 82.56 | 36.87 / 35.02 |
| NR→SR ON | 62.05 | 62.97 | 97.33 / 90.00 |
| 再次 OFF | 80.73 | 82.87 | 74.13 / 62.21 |

ON 平均 FPS 约 +1.49%，再次 OFF 插件执行采样率约 -16.1%，但只是一轮
有后台差异的观察，不是普遍收益承诺；整个 ntdll 也不是都下降。
Perf9 关闭后恢复自身 FPS，插件仍从首次 OFF 35.02 增至 62.21 ms/s。

新的独立解析不使用旧函数映射作命名推断，专门复算进程/模块 CPU、调度
时间片、全部采样中的编译器进程和完整帧间隔。两份 lost events/buffers、
重复帧起点和缺失 DisplayedTime 均为 0。FPS 使用 1000/平均 FrameTime，
选窗 [2,10)、[21,29)、[34,42) 秒，并检查前后偏移0.5秒的敏感性。
CPU使用同稳态内显式UTC窗口，未与CSV做精确QPC合窗，因此没有计算
CPU-ms/帧。GPUBusy 是目标进程的引擎工作时间，不是物理 GPU 利用率。

首次开启长帧约1777→613ms；Feature18创建日志间隔约1367→131ms。
本候选及此前Perf9没有修改Feature18创建逻辑，加载/驱动缓存和初始化
历史可能不同，不能把它算作本批修复收益。维护者后续F6热切换不明显卡顿
的反馈保持不变，不将冷启用结果泛化为每次开关都会卡。

## 冻结源的检查边界

仅有两个生产文件改变：`nr_command_state.inl` 与
`nr_source_frame_runtime.inl`。全部 root-argument 消费者已定位：恢复先看
kind，再用 constant_mask 读有效词；快照可复制已初始化的无效载荷，但不
重放它。没有字节比较/序列化绕过这些门控。Reset仍处理全部头字段、动态
状态、null-guard/meta/序号以及COM引用；原生Reset/ClearState行为不变。

GuideCopy发布把recorded=true与guides_awaiting_submission=true放在同一
source_lock中；只有遍历全部已记录且未提交、未poison的副本后才可清false。
Reset可留下保守true，但不会从false创造新待提交副本。新OnExecute在原锁内
使用这个精确无工作证明，保留所有实际Signal、队列身份、失败及poison语义。
该消费者优化不跳过真实GPU副本，也不把未完成副本标为完成。
