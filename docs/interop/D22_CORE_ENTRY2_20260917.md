# #223：在真实 Core Create 之前覆盖，不猜 Evaluate 别名

基线：`codex/d21-shadow-lockperf-buildfix-20260916 @ d8de528f4df23999c4f6711320a94ac522e0f44e`。
候选：`beta0.5-dline22-coreentry2`，保留该分支所有 lockperf1 和构建修正。

## 这次复测改变了什么

维护者的 sottr1 F8 显示：模型层 Feature1 Create 成功，首次 Core Evaluate 仍未知；`directCoreWrapperAliases=0`，`loaderInitHooksReady=0`，`loaderInitCompletions=0`，`coreLifecycleReady=1`。原生参数样本、NR、导引捕获都未开始。采集结尾虽是 OFF，但同进程先前 ON 切换也没有成功工作，不归因于采集时开关。

已逐文件确认 d8de528 的做法是“未知 Evaluate + 来自 wrapper 的返回地址 + 唯一已知 Feature1”补别名，并把内层保持 native-only；不是上一份独立源码候选的 pre-Create 入口拦截。它的测试将真实 caller 检查替换成 true，并人工再调用公开 wrapper Evaluate，不能证明游戏采用此转发方向。日志也不包含当前 helper 的逐项拒绝原因，因此不猜这次具体是哪一项失败，更不把两个诊断 token 当作真实指针不同的证明。

## 本候选

只撤回 d8de528 的四项 alias 运行时/导出/测试改动，精确恢复到它的父提交相应文件，再通过既有生成器接入真实 pre-Create 覆盖。未恢复旧全局独占 setter 锁，未修改 RR/FG/模型/颜色/多层/描述符低开销路径。

新模块观察实际 `_nvngx.dll` D3D12 `CreateFeature` 的动态地址取得；仅此已解析成功的目标可以返回类型匹配的 thunk。实际调用 thunk 时，在进入原生 Create 前使用既有生命周期安装器完成覆盖。GetProcAddress 内不创建/启用 detour，不调用 Init/Create，不加载新模块，不取消已有隔离，也不伪造句柄。原生结果和输出保持原样；同一个真实原生调用只转发一次。

自模块导出检查、序号、其他符号/模块、私有 NR、冲突目标均保持原地址。一个进程仍只有既有的唯一 Core 支持范围。Core 已覆盖后的动态地址查询走短路。额外观察在动态导出查询/冷启动，不挂 Draw/Dispatch，不每帧扫描模块。

Worker 最开始安装解析边界；并补上“只有 Core 已加载、模型/loader 尚无可观察入口”的强制冷扫描。Init 已经被游戏调用或静态 SDK 缓存、但未落到我们的 nvngx Init detour，不再是本机制必需的前置条件。**若解析地址在 addon 安装之前已缓存，或游戏绕过该 Win32 resolver，本候选不能回溯它；新计数必须如实揭示，不宣称已覆盖。**

## 必须实际执行的构建

在本候选干净提交上使用已有 D21 的依赖参数：

```powershell
./scripts/build-d22-coreentry2.ps1 -UpstreamRoot <same-carrier> -ToolchainRoot <same-llvm-mingw> -ReShadeSourceRoot <same-reshade> -DirectXMathRoot <same-math> -OutputRoot <new-output> -NrchainReuseRoot <previous-verified-nrchain>
```

可选的 NrchainReuseRoot 按原构建情况省略。脚本运行真实 Win32 GetProcAddress/MinHook 的隔离假 NGX DLL 正负对照，再执行原完整双语/WARP构建。它检查完整生成产物确实接入 helper/worker/F8，而不是仅改标签。保留 linker MAP 与哈希，普通 Core 测试文件独立输出，不自动部署游戏。

## 用户只需最小验证

先全新游戏进程；默认前置，保留原 INI 和其他依赖。不要求重复做 CPU/RR 六组。成功必须有真实 NR 采用和可见效果；F8看到入口成功但 NR 仍为零，不能算游戏修好。

F8 的 `coreEntry` 区分：resolverReady、resolutions、createEntries、coveredBeforeCreate、uncoveredBeforeCreate。coreLifecycleReady=1只说明观察器当前就绪，不是当前句柄的历史证明。即使 resolver 没命中，冷扫描也可能正确捕获 Core Create，应以真实分层 Create 记录为准。

如仍失败，只返回一次当前完整 F8。没有任何 `coreEntry.schema=1` 时先检查二进制身份和生成产物，不能继续套旧标签的日志。`loaderInitHooksReady=0` 本身不再作为失败判据。

## 验证边界

云端主机可验证实际源片段和生成器，不能替代真实 Windows detour、GPU或游戏。Windows命令通道不可执行时明确标为未运行；不要将之前 sottr1 的通过结果继承成本候选通过。问题 #223 保持开放，未授权替换稳定发布。
