# Corefix.4 复测：共享状态窗口、Feature 重建与证据保持

维护者确认死亡搁浅仍看不到持续 NR 效果，近期状态仍跳；绝区零仍出现 unsupported format。两份完整 F8 的源身份均为 `8693e2e48cafa4c7f9451a3a5c21e653c61ea1c4`，中文 Core SHA-256 为 `36f71482a32e084b350a51ab13ec8e8d5d77aced470bd817633535afe9fcee0b`，报告未截断。此前本地 CPU、编译、菜单及 WARP 通过不能替代这次实机失败。

本次接续以交付后的文档提交 `50660bfe529e789d0edfde119782b873df387271` 为基础；它相对于运行源只增加交接文档。原始 TXT、对象编号、时刻及本地路径保留在私有证据目录，不进入源码发布。

## 死亡搁浅的近期状态

F8 区间明确为暂停自动采样。UI 回执显示，在相同配置、相同观察 epoch、计数持续增加且没有回退时，一个绘制线程刚把状态更新为“已观察到 NR”，另一线程 63 ms 后因自己的 2156 ms 调用空档重置为“正在检查”。生产计数为进程范围，Window 却属于线程局部存储；这已足以定位一类虚假的状态回退。

末尾另有约 26.7 秒的全局已发布 UI 回执空档。它不能解释为其他线程始终在绘制，也不能仅凭回执认定菜单被关闭。修复必须保留真正全局停读后的失效，不得通过延长阈值或强行保持成功文案隐藏空档。

## 绝区零的格式转折

本次进程曾记录 84 次 NR、82 次提交；当前 F8 区间载体继续增长，而 NR、提交不再增长。日志显示原生 Feature 重建后从处理转为格式未知。旧的存储样本使用 R8G8B8A8_TYPELESS 资源和 UNORM 视图，当前仍是同一资源生命周期、相同配置，但属于新的 Feature 代。

现有格式 Ledger 按设备、资源、Feature 代和角色隔离，只接受同步原生 CreateView。新 Feature 复用既有描述符时，新代没有创建事件，后续成功调用也不能恢复类型。旧代的 UNORM 证据不得直接移植；设备支持候选格式也不能替代当前原生使用证据。

Corefix.4 的原生设备/列表关联在本次已得到确认：两游戏的当前 native-use 身份、hook 和原生调用成功均为真，Output clear 已识别，未再把同一调用计为其他列表。剩余丢失发生在描述符记录：死亡搁浅是 slot unknown，绝区零是 heap unknown。两个值都不等于游戏传入非法描述符。

## 描述符表的确定缺口

原版生产 header 的纯 CPU 反例通过 20 条断言。它们证明下列行为可以在对象从未退休、记录容量仍有大量空位时出现：

- 两个 heap 的编号相差 256，后者直接替换前者，剩余空位不被利用。
- 两个 resource 的编号相差 2048，仍存活的 Output 从地址及 inventory 查询中消失；旧 descriptor 随后显示 resource retired。
- 同一 heap 的两个 slot 相差 8192，仅两次写入就让第一份描述符失去记录。
- 新 Feature 代成功复用既有视图，但没有 CreateView，格式 Ledger 一直未知；旧代证据仍存在。

实机报告中全局描述符淘汰接近写入数量，与这种保持缺口一致；汇总计数仍不能恢复恰好哪一份 Output 描述符被何时替换。CPU 反例证明记录机制缺陷，不证明最终画面故障已定位。

## 死亡搁浅的实际存储与最终显示

暂停阶段 NR 和提交各继续增加 26。当前只读边界已记录原生 Output clear、准确列表身份及提交数组位置，但当前阶段没有新 GPU 存储样本。保留的旧正常阶段样本有 2040 个实际点、1065 个期望点，存储比较仍未知。

期望统计会排除 UNORM 存储结果不唯一的点；实际统计包含全部点。两者集合不同，不能比较其 hash 或均值来认定写错，也不能将发生变化的实际点当作完整匹配。下一步比较须使用同坐标、同次调用的合法编码集合，并保留非有限值、丢失样本和身份失配检查。

当前只读边界中的两个 Output 状态切换是 shader-resource 与 render-target 之间切换；它们在 CPU 中的记录顺序与 Execute 数组位置相反，数组位置分处 NR origin 前后。不能据 CPU 序号重建 GPU 状态时间线或推测性修改 StateBefore。RT 绑定、绘制及 RT 清除的目标仍未知；同设备 Present 只关闭观察窗口，尚不证明 Output 被最终消费者使用。

## 接续边界

近期状态先修复进程计数与共享 Window 的归属。描述符记录须按完整键与真实生命周期保持，并区分缓存存在、当前明确使用、提交时有效和最终图像。格式恢复必须基于当前 Feature 的充分证据，不能默认 UNORM、沿用旧代成功或仅以缓存存在放行。

实机视觉失败继续保留。后续源改、本地验证、冻结构建和实际部署须分别记录；此文档本身不宣称新候选已交付。
