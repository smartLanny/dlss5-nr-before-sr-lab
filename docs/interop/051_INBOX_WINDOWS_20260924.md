# 0.5.1 Beta Inbox1: Windows接续、原始证据和验证边界

本候选接续 #306/#300，最终研究目标仍为next/0.5。它不是回到旧Perf分支，
也没有重做已经合入0.5.1的#303、Perf12或画质/时域功能。冻结构建来源为
`4a07bce25fa22fb10f6b9653eb61a56d800307f0`，本次完整进程passed/exit0。
不借用旧0.5.1的GPU结果；实际游戏与NVIDIA推理仍未验证。

## 本轮原件核验与更正

原始来源为维护者Windows的三个指定inbox。逐个读取F8或完整游戏日志，
记录原文件SHA256、实际构建、GPU、进程和时间窗口；原始路径、完整日志及
私人标识不提交到公共源码。聊天中旧Perf10/5080的F8不是本批0.5.1证据。

小小墨瑟的0x3C0精确对应NRChain_Init/Create/Evaluate/Release四个导出。
当前源码先获取DLL句柄，再分别GetProcAddress；四项失败后禁止NR执行。
因此更准确的描述是**桥接接口解析失败且两种加载观察不一致**，可能是
错误/旧/被替代或重定向的文件，尚不能仅凭此确定其中哪种情况。匹配的
Core+nrchain和重启后新F8是最小验证，不应盲目替换已加载的NR模型。

### 显存口径

你是360的两次采样均为local CurrentUsage=13,516,349,440字节，
Budget=14,253,277,184字节，即约12.59/13.27 GiB，尚余702.79 MiB，
占预算94.83%，overBudget=0。它是全进程DXGI账目，不是NR独占用量或
整设备占用，也没有给出时间曲线。余量较小值得重视，但不能凭一个窗口
断定分页造成掉帧；系统/驱动/游戏本身的占用不能全部记到插件名下。

该份请求Before，但实际因RR走After，RR后置请求60%；当前主实例与历史
双层字段应分开，不能拿不同实际路线/尺寸和不同进程比较“版本节省”。
记录中auxiliary和temporal账目为零，主层/NGX内部和游戏资源仍存在。

### ETL路径实际指向的版本

#298的PATHS-FOR-AGENT明确说明“此人只有F8，没有他的ETL”，所列的是
共享旧#277 D13/D21 OFF材料。#277 ETL-PATHS也标记这两份为9月16日记录。
没有将它们当作9月23日三位0.5.1用户的新录制，也没有重新套用旧汇总的
CPU差值/FPS。需要时这些旧记录仍能复核历史优化，但不能替代同进程新证据。

## 实际修复与保持的保护

#306用实际选择/退休/收集/释放函数复现：同carrier旧主层或辅助仍在等待
自身recording/fence/binding等条件，待销毁队列却为空时，新模型获准分配。
本补丁将同来源未完成退休纳入创建准入；已有匹配实例和正常F6缓存保留，
无关来源不被新的本地条件拖住，原全局queued/releasing约束仍在。

等待时沿用原生SR/RR，保存请求的路线/比例；不绕到Present再创建另一份。
不添加CPU等待/Flush、不强制释放、不固定等几帧清空、也不解除EMT的
未知生命周期隔离。提示解释正在等待安全释放，持续时要求F8反馈。

这项修复针对**配置/尺寸改变时的重叠峰值**，不是减少正常活动模型的
内存需求，不声称解释你是360当前单主实例的全部占用，不增加自动降画质。
更严格准入可能延长替换期间的原生画面窗口，这是需要单独验收的风险。

## Windows恢复和构建修正

默认product目录仍是历史快照，本轮接续已有0.5.1 recovery工作树，不重置
它或覆盖其他Agent功能工作树。此前已有898ca26b的运行时补丁，aaa4a473
添加独立inbox1身份，4daafed5保留画质源固定校验；本轮不重复实现它们。

此前完整Windows尝试停在时域模块：SDK输入为空导致--sdk参数缺值，而不是
NR代码或GPU读回失败。找到并验证现有的干净固定FidelityFX SDK、匹配编译器、
对齐修正收据及8个缓存对象。新增显式-FfxSdkRoot/-FfxCacheRoot参数，
缺路径在昂贵构建前失败，仍由真实模块验证精确SDK/编译器/对象哈希。
仅在构建调用内设置环境，finally恢复调用方环境，不改系统环境或共享SDK。

实际入口的三个编排测试覆盖缺输入、无效路径、子流程失败及环境恢复。
该测试用合成子流程，只证明编排，不冒充Core或GPU。随后使用完整统一入口
重新生成、双语编译、完整人脸后端、累计性能/来源/图形和新增创建门禁，
再执行生成Core的HDR时域/集中验收/辅助shader/原生O检查。

打包器将精确的unified10-inbox1映射到unified10验证要求，但保留自己的
版本/提交/二进制身份。不得因为多一个后缀跳过人脸、AMD许可证、60场景
后置WARP或扩展Core测试。包内附本说明而非把旧0.5.1GPU回执当新包结果。
