# 当前执行窗口与存储比较分开说明

基线为 `bba65ebd`（当前 `corefix.1` 候选的交接源）。本项对应 #203 的
诊断解释缺口，不将 #205 的死亡搁浅 1 后置弱效果或闪烁记为已修复。

## 已确认的问题与改动

恢复账本的 `correlated_window` 单独证明当前尝试的连续 NR、原生调用和
匹配提交；`proof_attempt_id` 由成功存储比较产生。死亡搁浅 1 新反馈中，
实际采样为 2040 点，期望可比较部分为 1079 点，因此比较仍未知。此前
判定器将存储证明 ID 缺失同时解释成整个执行窗口缺失，F8 也隐藏了已有数值。

现先保留当前作用范围与尝试下的描述符、原生、NR 和提交门槛，再判断存储。
已关联执行但存储证明缺失或来自旧尝试时，判定为 `writeback` 阶段的
`storage-comparison-unverified`，明确缺少本次存储比较及后续消费者／Present
验证。真实短调用窗口、缺失提交和实际失败继续分别显示各自原因。

F8 新增 `executionWindowAvailable` 与 `storageComparison`，已有
`proofWindowAvailable` 保持同时需要执行窗口及匹配存储证明 ID 的含义。
执行数值不再依赖存储证明 ID；失败尝试不能继续显示有效成功窗口。
`storageComparison=unknown` 包括未取得、不完整或过期的比较；改变的样本
本身不能证明符合期望，也不能证明写错。历史证据保留自己的作用范围，
`current` 与顶层判定继续阻止它认证新配置、Feature 或模式。

`pending` 是证据状态。该模块只读快照，不关闭 NR、不提交额外调用，也不
改变账本准入、失败锁存、等待预算或运行重试权限。没有完整写回证明时，
不会进入 `needs-visual-F7` 或声明恢复成功；已有完整技术证明也不等于最终
消费者或画面通过。该认证范围仍仅为已分类的 Feature 1，RR 使用独立诊断。

## 本地验证

以下均为 CPU 检查，输入是合成事实，没有执行 GPU、NGX 或游戏：

- 实际 Verdict：65 项，另含 4 个指定失败检查；覆盖部分比较、旧存储 ID、
  旧作用范围、短调用／提交、真实写回失败及完整写回要求。
- 实际 F8 writer 与生产追加／容量合同：5902 项，另含 4 个指定失败检查；
  包括重新引入“没有存储 ID 就隐藏 NR 数值”的旧行为必须失败。
- 生产账本→快照→Verdict→F8：69 项，保留 4 个 RR 范围负对照；当前完整
  执行、未知存储继续允许正常尝试，真实比较失败仍锁存。
- 全部 F8 writer 与实际 TXT／ZIP 采集：95 项；覆盖 POST R10 形状的
  `2040/1079` 部分比较、执行 `3/3/3`、未知存储及消费者缺口同时保留。
  最大组合文本为 115384 字节，必需尾部与 UTF-8 完整。

验证命令入口为 `validate-compatibility-verdict.py`、
`validate-compatibility-verdict-feedback.py`、`validate-compatibility-rr-scope.py`
和 `validate-feedback-combined.py`。日志、源文件与二进制哈希保存在本地验证
产物；最终集成候选还需使用组装源码重跑相关门禁。本项没有修改版本、
发布状态或任何游戏画面算法。
