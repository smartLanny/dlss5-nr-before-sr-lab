# 直接 FSR 3.1 输入映射与 DLSS SR 受控 GPU 样本

Refs #14 / #163 / #164 / #167。本切片保持原生 DLSS 路线无 Opti 依赖，首先
验证公开时域输入描述能直接接官方 NGX SR。NR 仍由本项目 Core 单独处理。

## 已实现

`src/interop/nr_fsr31_dlss.h` 消费官方 FFX 1.1.4 的 upscale create/dispatch
结构，核对实际 D3D12 设备、资源及活跃尺寸，生成官方 NGX 创建和评估参数。
不是用同名字段猜测元数据，也不需要 OptiScaler 的源码、DLL 或 NR owner。

- R/N/O 分工保留：本切片只做真实 R→O SR；N 和 NR 属于 #171 的外部 Core 接口。
- FFX backend DX12 扩展必须与实际设备匹配；未知或循环扩展拒绝。
- 第一版支持同设备、单 mip/array/sample 的线性 FP16 RGBA、FP32 硬件深度、
  RG16F motion，输入 compute-read、输出 UAV。检查描述与真实 GetDesc 一致。
  输出不得与输入别名，输出尺寸必须匹配 O；输入活跃区可小于实际资源。
- 按真实 DLSS capability 查询每个质量档的推荐/最小/最大 R 范围，再选择覆盖
  当前 R 和创建上限的档位。没有把所有比例固定为 Quality，也没有篡改游戏 R。
- 保留像素 jitter、运动缩放、reset、preExposure、帧时间、低/高分辨率 motion
  和深度反向标记。非有限/零运动缩放/非法曝光拒绝，避免 helper 的默认值替换
  掩盖缺失输入。
- 非线性/PQ/sRGB、尚未映射的反应/透明蒙版、锐化或其它未知功能明确拒绝，
  不把 FSR reactive mask 盲当 NGX BiasCurrentColor。

`tests/direct_sr_gpu.cpp` 是可执行的受控渲染器，实际构造纹理、填写上述 FFX
结构、调用生产映射及官方 NGX Create/Evaluate、提交并等待真实 fence，读回 O。
它没有加载 AMD FFX DLL 或拦截游戏 API；不能把这个成功称为游戏注入已经完成。

## 已运行的验证

RTX 5090 Laptop 上的最终硬件运行：

| 阶段 | 实际结果 |
| --- | --- |
| 标准 Custom Project NGX Init / capability | 均 `0x1`，SR available=1 |
| 查询质量 | Performance，范围 640×360 至 1280×720 |
| 输入 / 输出 | R=640×360，O=1280×720，静态已知时域输入，jitter=0 |
| Create / 3 次 Evaluate | 均 `0x1` |
| 提交 / 完成 / 读回 | 每次 Execute + Signal + 实际 fence 完成后读回 |
| 像素 | 每帧 3,686,400 个 RGBA half 全有限；不同 XY 的 RGB 样本约 0.05017 / 0.79980 |
| Release / 两个参数块销毁 / Shutdown | 均 `0x1` |

输出随时域积累变化，三帧哈希不同，未声称达到时域收敛或逐帧完全相同。空间
变化检查只统计 RGB，避免 alpha=1 让全黑画面误通过。

另用真实 WARP 设备/资源完成 16 类映射边界检查：设备扩展、循环/未知扩展、
颜色域、两类蒙版、jitter/MV/曝光、质量范围、输出别名、状态、格式和跨设备。
WARP 的质量范围是显式夹具输入，不冒充 NGX capability 或 DLSS 推理。

测试中发现并修复了宿主自身的 move-only 事件 HANDLE、自指向 backend 描述的
返回后重绑、读回后恢复 UAV，以及 capability 参数块销毁。Signal/事件绑定/
等待失败和 `UINT64_MAX` 设备移除值进入测试进程的明确失败退出，不在未证明
完成时用异常展开释放 GPU 引用。早期失败日志保留，不计通过。

## 精确来源与复现

- AMD FidelityFX SDK `v1.1.4` / `c6efa6bf7f2027b3ec94f28578bb5965eabb9e55`，
  [官方 FFX API](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/tree/c6efa6bf7f2027b3ec94f28578bb5965eabb9e55/ffx-api/include/ffx_api)。
- NVIDIA DLSS SDK `a291cc7d2cc642a51566f3dfd5376f635cd1b284`，
  [官方 SDK](https://github.com/NVIDIA/DLSS/tree/a291cc7d2cc642a51566f3dfd5376f635cd1b284)。
- SDK 的头、静态库和运行时均保持仓库外；脚本固定 10 个实际 ABI/载荷哈希。
  NVIDIA SDK 不作为本仓源码重新分发。原始 AMD 头直接编译，没有伪造 FFX 导出。

```powershell
./scripts/validate-direct-sr-gpu.ps1 -Mode Both -FfxRoot <ffx-api-root> -DlssRoot <dlss-sdk-root> -EvidenceDirectory <new-output>
```

脚本支持独立 SDK/VS 路径，拒绝覆盖既有 evidence，产物/对象文件只写新目录。
输出 source commit/dirty、生产头/测试/脚本/EXE 与依赖哈希，分别记录 WARP 和
hardware 运行。测试不会部署游戏组件或修改驱动 profile。

## 尚未完成与接续接口

当前 `game_verified=false`、`NR=false`、`FG=false`。没有通用 TAA/TSR 提取、
游戏 FFX DLL 拦截、自动部署或真实游戏画面验收。这个 adapter 只用于确实缺少
DLSS 且有可用 FFX 合同的路径，不向已有原生 DLSS 游戏加转换层。

下一步按指定非 DLSS 游戏固定接口版本，在其真实 dispatch 边界接入，复用
现有命令/队列/完成契约；不能在已被失败调用修改的命令列表上盲目重跑原生 FSR。
未知 resource state 或被忽略的 mask 必须先保持原路线。

与 #171 的 Core 合并顺序已查清：标准 NGX Init → 强制 Query 安装观察 → Claim
外部 provider → Create SR → 当前帧 NR Submit → SR Evaluate → 真实完成等待 →
Release SR → Release provider。其 owner 旁路用于避免 SR 再调用第二次 NR；不能
在未观察 SR Create 的情况下仅靠晚 Claim 绕过 unknown-handle 保护。联合实证
在独立后续实验中进行，不计入上述 SR-only 结果。

FG #167 还需要呈现时存活的 HUDless/UI、相机常量、源帧身份、Reflex 和唯一
presenter；FFX SR dispatch 本身不足以证明这些条件。官方 FG-only 样本独立验证，
SR Create/Evaluate 成功不能充当 FG 插帧成功。
