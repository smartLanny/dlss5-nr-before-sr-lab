# Beta17 候选：取得 Windows 后的集中验证

先看下载工件对应的源码 SHA、Actions 结果和 `package-receipt.json`。云端完整构建
成功说明编译、CPU 和受控 WARP 检查通过；NVIDIA 实际模型、游戏画面与帧时间仍需
你的机器确认。当前已交付回退基线仍是 [Beta14](../interop/052_BETA14_DELIVERY.json)。

## 准备

保留现用安装包、配置和可用存档，记下游戏版本、显卡、驱动、分辨率及 SR/RR、HDR、
FG 状态。按现有安装方式选择对应语言的 Core 候选。Core-only 包不附 NVIDIA
运行库，也不要求为这次测试更换已在用的运行库。不要把不同构建的 Core 和项目
`nrchain_nvngx.dll` 混配；两者身份由同一包的 manifest 和回执记录。

进入一个能够重复的场景，先记录现有设置。每一步只改对应的一项，失败就保留该步
反馈；无需把后面的实验全部跑完才能提交问题。

## 按顺序检查

| 步骤 | 操作 | 要确认的现象与记录 |
|---|---|---|
| 1. 默认路线 | 沿用普通恢复与一层，观察画面；用 F6 关闭再开启 | 游戏保持原生回退；开启后实际运行状态与 NR 调用推进相符。无效果、明显闪烁或旁路时按 F8 |
| 2. 菜单与重建 | 反复开关游戏菜单，切换已有的处理位置，再回到原设置 | 重点检查 #317/#339：菜单结束后能恢复，持续旁路有可分析反馈；记录是哪一步开始失效 |
| 3. 层数与模型 | 一层→两层→一层；按需试一次全局/逐层网络并恢复 | 配置摘要正确，未启用层的自定义设置保留；F8 的请求、创建、执行证据分别看，不凭菜单名字认定模型已经运行 |
| 4. 画面细节 | 同一场景检查近黑、人脸、字幕、细边与运动；可选再试 Continuous SDR | 先保留基线，再单独比较新增色控。颜色/闪烁问题用 F7 拍新的一组，不把不同设置截图混成同帧证据 |
| 5. FG 共存 | 若游戏已有 FG，比较开/关及 F6 切换，正常退出并重新进入 | 观察卡住、持续旁路或画面异常；记录实际后端与插件。云端锁序测试不能替代这一步 |
| 6. 稳态与显存 | 在同一路线、同一模型、同一场景持续运行，重复菜单与层数切换 | 保留开始和结束的 F8；看帧时间及显存趋势。F8 的已知分配、DXGI 进程用量、模型前后差值是不同口径，不能互相相减就当成泄漏或节省 |

私有 SR、空间及时域实验在上述基线稳定后再分别开启。本轮没有把 #340 的未验收
预算准入或 #342 的双 RR 研究宿主当作已完成产品功能。更多层数、一次成功创建或
旁路时 FPS 上升，都不能直接作为画质/性能收益结论。

## 提交一次有效反馈

普通不生效、菜单恢复或设置切换问题，保留本次 **F8 原始 TXT**，补上复现步骤和
预期现象即可。也可以在任何装有 Python 的电脑上整理报告：

```sh
python scripts/feedback-report.py feedback.txt --output report.md
```

图像问题按 F7 后，保留它新生成的一对核心 ZIP 和图像 ZIP。不要拿旧 F8 文件替代
新核心包。报告工具支持：

```sh
python scripts/feedback-report.py core.zip --image images.zip --symptom visual --output visual-report.md
```

这些命令只检查与整理本地文件，不会上传、改游戏设置或覆盖旧报告。部分采集也
可以分析，工具会说明缺失；保留原文件。退出后崩溃则沿用离线崩溃收集器，F8
不能替代异常栈。提交前核对报告内容，原始 dump 和私人日志不要直接公开。

## 结果如何记

每个结论记录“源码/包哈希 + 游戏与设置 + 操作步骤 + 反馈文件”。一款游戏的成功
不自动覆盖其它 API、显卡或实验。发现回归时回到同一 Beta14 包与原设置复测，保留
两份各自身份的反馈；不要重命名旧包来充当新候选。
