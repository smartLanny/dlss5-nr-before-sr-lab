# Beta17 候选：取得 Windows 后的集中验证

先看下载工件对应的源码 SHA、Actions 结果和 `package-receipt.json`。云端完整构建
成功说明编译、CPU 和受控 WARP 检查通过；NVIDIA 实际模型、游戏画面与帧时间仍需
你的机器确认。当前已交付回退基线仍是 [Beta14](../interop/052_BETA14_DELIVERY.json)。

## 准备

记下游戏版本、显卡、驱动、分辨率及 SR/RR、HDR、FG 状态，并保留可用存档。
替换文件前先退出游戏，将现用 Beta14 的 Core `.addon64`、配套的
`nrchain_nvngx.dll` 和配置复制到插件搜索目录之外，记下各文件的原路径。
Core 的配置文件是与 Core 同目录的 `nr_before_sr.ini`；还应备份现用的
`ReShade.ini` 和 ReShade 预设。某个配置原本不存在时也记下来，回滚时需要还原
这个状态。保留原 Beta14 安装包，不用测试过程中改过的 INI 覆盖这份备份。

按现有安装方式选择一种语言，将同一候选 OTA 内的 Core 与 `nrchain_nvngx.dll`
一起替换到原安装位置，插件搜索目录中只保留一个版本、一种语言的 Core。
其它插件与已有运行库保持原样。Core-only 包不附 NVIDIA 运行库或人脸资源，
也不要求为这次测试更换它们；Core 与配套桥的身份可查同一包的 manifest 和回执。

先在 **开发者 → 快捷键** 查看当前绑定。默认 F6 开关 NR、F7 采集画面、F8 生成
文字报告；下文用这些默认键指代相应动作，实际操作以当前界面显示的键位为准。
可以在这里改键，避开游戏和 ReShade 已用按键；改键后先松开再按。若绑定为
“关闭”，可用 NR 总开关，或反馈页的“采集当前画面”“生成文字报告”按钮操作。

进入一个能够重复的场景，先记录现有设置。每一步只改对应的一项，失败就保留该步
反馈；无需把后面的实验全部跑完才能提交问题。

## 按顺序检查

| 步骤 | 操作 | 要确认的现象与记录 |
|---|---|---|
| 1. 默认路线 | 沿用普通恢复与一层，观察画面；用 F6 关闭再开启 | 游戏保持原生回退；开启后实际运行状态与 NR 调用推进相符。无效果、明显闪烁或旁路时按 F8 |
| 2. 菜单与重建 | 反复开关游戏菜单，切换已有的处理位置，再回到原设置 | 重点检查 #317/#339：菜单结束后能恢复，持续旁路有可分析反馈；记录是哪一步开始失效 |
| 3. 层数与模型 | 一层→两层→一层；按需试一次全局/逐层网络并恢复 | 配置摘要正确，未启用层的自定义设置保留；F8 的请求、创建、执行证据分别看，不凭菜单名字认定模型已经运行 |
| 4. 画面细节 | 同一场景检查近黑、人脸、字幕、细边与运动；可选再试 Continuous SDR | 先保留基线，再单独比较新增色控。颜色/闪烁问题用 F7 拍新的一组，不把不同设置截图混成同帧证据 |
| 5. FG 共存 | 若游戏已有 FG，比较开/关及 F6 切换，正常退出并重新进入 | 观察卡住、持续旁路或画面异常；记录实际后端与插件。云端锁序测试不能替代这一步 |
| 6. 稳态与显存 | 在同一路线、同一模型、同一场景持续运行，重复菜单与层数切换 | 保留开始和结束的 F8；看帧时间及显存趋势。F8 的已知分配、DXGI 进程用量、模型前后差值是不同口径，不能互相相减就当成泄漏或节省 |

私有 SR、空间及时域实验在上述基线稳定后再分别开启。本轮没有把 #340 的未验收
预算准入或 #342 的双 RR 研究宿主当作已完成产品功能。更多层数、一次成功创建或
旁路时 FPS 上升，都不能直接作为画质/性能收益结论。

## 提交一次有效反馈

普通不生效、菜单恢复或设置切换问题，保留本次 **F8 原始 TXT**，补上复现步骤和
预期现象即可。触发文字报告后，等反馈页显示保存结果；成功时会自动复制文件路径，
可粘贴到文件资源管理器的地址栏找到文件。若自动复制失败，在反馈页查看本次的
完整路径或保存错误，不要把剪贴板里残留的旧路径当作本次结果。

报告默认写入 Windows 系统“文档”目录下的 `DLSS5-Feedback`；该目录创建失败时，
程序会尝试 `%TEMP%\DLSS5-Feedback`。进入本次生成的子目录，找文件名带有日期、
游戏名和版本的 `.txt`。系统“文档”可能被重定向，优先使用程序显示或复制的完整
路径。本次没有生成新文件时，记录保存状态即可，不拿旧报告替代。

也可以在任何装有 Python 的电脑上整理报告：

```sh
python scripts/feedback-report.py feedback.txt --output report.md
```

命令中的 `feedback.txt`、`core.zip` 和 `images.zip` 是占位文件名，请换成自己的
原始文件路径；路径包含空格时加双引号。

图像问题按 F7 后，按反馈页显示的实际采集路线收集文件。普通前后置路线会生成
配套的核心 ZIP 和图像 ZIP；等本次生成结果出现后，分别复制两个包的路径。
不要拿旧 F8 文件替代新核心包；若只生成了部分数据，同时记录缺失原因。
报告工具可以整理这对 ZIP：

```sh
python scripts/feedback-report.py core.zip --image images.zip --symptom visual --output visual-report.md
```

若当前是 Present 或帧生成前的兼容路线，F7 会请求导出当前处理层并生成文字报告，
不会生成上面的一对 ZIP。等反馈页显示对应的 Present／FG 各层数据已导出，再到
系统“文档”下的 `DLSS5-Present-Capture` 或 `DLSS5-FG-Capture` 保留本次子目录，
连同本次 TXT 一起记录。这些是处理层数据，不是最终游戏屏幕截图；仍在导出或
采集失败时，按实际状态记录，不拿旧目录当作本次结果。

这些命令只检查与整理本地文件，不会上传、改游戏设置或覆盖旧报告。部分采集也
可以分析，工具会说明缺失；保留原文件。退出后崩溃则沿用离线崩溃收集器，F8
不能替代异常栈。提交前核对报告内容，原始 dump 和私人日志不要直接公开。

## 结果如何记

每个结论记录“源码/包哈希 + 游戏与设置 + 操作步骤 + 反馈文件”。一款游戏的成功
不自动覆盖其它 API、显卡或实验。

## 回滚到 Beta14

测试中的层数、网络、色控和快捷键操作会保存到 INI；只换回旧 Core 不会恢复测试前
的设置。发现回归时按下面的顺序复测：

1. 先保留候选的反馈与当前配置，再退出游戏。
2. 将候选 Core 和 `nrchain_nvngx.dll` 移到插件搜索目录之外，从同一份 Beta14
   备份或原包恢复配套的两个文件。确认搜索目录中没有留下第二个 Core。
3. 把测试前备份的 `nr_before_sr.ini` 放回原路径；若改过 ReShade 配置或预设，也
   恢复对应备份。原本没有某个 INI 时，先把测试新建的文件另存，再移出原位置。
4. 重新启动游戏，确认显示 Beta14，并核对原设置、原键位，再复现同一场景。

分别保留候选与 Beta14 的反馈和包哈希；不要重命名旧包来充当新候选。
