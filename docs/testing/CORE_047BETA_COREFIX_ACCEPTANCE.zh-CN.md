# 0.4.7beta-corefix.1 Core 验收说明

这一候选把资源语义、曝光读取、分层 NGX 生命周期和后置写入诊断集中在同一个 Core 中。包内只有对应语言的 Core、配套 nrchain_nvngx.dll、许可和构建凭据。保留原有游戏设置与 NR 运行库；切换语言时只保留一个 Core。

## 本次行为

- 优先使用资源本身的确定类型，或本次原生 SR 调用实际创建的类型视图。只有显式合同和成功的设备查询能把候选缩减到唯一解释时，才采用唯一合同。不能确定就保留游戏原生 SR。
- 首次遇到未知资源时，正常的原生 SR 调用可以提供新证据。下一次正常调用会自动重试，不需要为了触发恢复额外开关功能，也不额外调用一次 SR 或 NR。
- 自动恢复必须关联实际描述符写入、NR 和原生 SR 返回值、真实队列提交，以及目标资源存储后的稀疏读回。三个连续关联调用和当前资源的读回证据齐全后，才报告技术恢复成功。当前解释发生确定失败时会锁存；换一个计数或重试次数不能冲掉失败。
- typed R8_UNORM 的 1×1 ExposureTexture 可以按最终曝光比例读取；R8 TYPELESS、整数和其他未证实的解释仍需独立证据。未执行设备查询会明确记录，不再被描述成驱动拒绝。
- 分层 Create、Evaluate、Release 的身份分别记录；外部 Feature 18 与 Core 私有 NR 区分。后置观察窗口在关闭后保持不变，配置和资源切换不会继续污染旧记录。

## 一次 F8 反馈

在正常场景保持当前设置，按一次 F8，提供生成的 TXT。无需先轮流试一批开关。结尾的 `decision.*` 是当前 Compatibility Verdict，包含阻塞阶段、原因、是否尝试恢复、首次确定失败、缺失证据和下一步。

- `auto-retry`：仍在等待确定语义或完整的本进程证据。日志会给出具体缺少哪一步。
- `needs-code`：当前事实已指向需要补代码的合同、观察缺口或失败；附同一份 TXT 即可继续定位。
- `needs-visual-F7`：技术写入证据齐全，最终画面还需要对照。此时再用 F7，并说明场景中的具体差异。
- `none`：例如总开关关闭或外部 NR 所有者正在接管；按日志的实际原因判断。

“已提交”不等于“最终画面已显示”，“技术恢复成功”也不等于全屏视觉效果已经验收。稀疏读回只证明报告中标明的资源、区域和时间窗口。

## 实机样本

本批用 #2 与 #202 检查 TYPELESS 资源的不同实际来源，用 #229《死亡搁浅 2》检查 typed Exposure 对照；#223/#107 检查生命周期和所有权；#205《死亡搁浅 1》继续检查后置存储与最终画面的关系。构建凭据中的 WARP 结果是本地软件 D3D12 验证，不能替代 NVIDIA NR 和各游戏的实际反馈。

本候选不自动改写游戏 INI，不包含 Manager 或 FG/MFG 后端，也不自动晋升到主分支或稳定版。
